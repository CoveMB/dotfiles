# Recurring coordination monitors

- Before creating or materially changing a monitor, verify current native scheduling capabilities. Define the active cadence, consecutive unchanged-check threshold, quiet intervals and cap, reset/recovery conditions, and retry/deadline handling. State expected detection delay assuming normal runs, separately from queue/runtime uncertainty and documented guarantees.
- Qualify quiet waits through fresh owner, runtime and checkpoint evidence with no eligible work or handoff. Controller idleness or notification silence does not establish inactivity. Missing/stale evidence or inspection failure earns no quiet credit; retain timely coordination while owners are active.
- Record each blocker's next actor and required action in the existing checkpoint: human input, orchestrator decision/handoff, or actual execution permission. A pending authorized orchestrator grant is coordination work, not a human-input-only wait. Reassess these dependencies when a human reply or worker notice arrives; do not carry forward a stale blocker classification.
- Backoff must reduce scheduled model wakeups. Notification suppression or prompt shortening alone is insufficient. If adaptive changes are unsupported, propose a supported fixed cadence with its limitations; do not build a scheduler.
- Require explicit approval for the chosen schedule and the precise conditions/bounds of future automatic schedule changes; reuse existing approval. Preserve ownership, pending decisions, notification preferences and completion rules; do not reactivate manually paused or completed monitors without an explicit human resumption instruction.
- When fresh owner, runtime and checkpoint evidence shows that progress depends entirely on user input and no independent work, handoff, deadline or external operation requires monitoring, save the checkpoint, pending question and return route before pausing. Specify the answer location and how it will wake the owning orchestrator, using the global worker-notification rule. If no authorized notification route is available, explicitly tell the user which orchestrator chat to return to and what to relay; do not assume a worker-chat reply wakes another chat. Pause the existing automation through the supported tool, verify its saved paused state, and notify the user once. This rule grants standing authorization for that pause without another confirmation; it does not override an explicit task-specific instruction to keep monitoring. If pausing is unavailable or fails, report that scheduling remains active or unverified; do not claim notification suppression stopped wakeups.
- For a monitor paused for user input, a human reply or authorized worker notice triggers reassessment of the original reply, current owner, checkpoint and remaining dependencies; a notice alone is not approval. When the reply permits authorized coordination or work to continue, resume the same automation at its previously approved cadence through the supported tool and verify its saved active state. Do not require downstream publication success before handling an eligible orchestrator grant. Keep an actually denied action stopped unless its normal permission control permits continuation; a notice alone does not authorize retry or bypass. An unrelated reply, unresolved answer that enables no work, or unrelated/manual pause grants no resumption authority. Preserve all other approval boundaries.
- While directly supervising an active worker, the orchestrator may keep a user-input-paused heartbeat paused temporarily. Before ending that supervision or yielding the turn with eligible work, a pending orchestrator decision/handoff, or an external operation needing monitoring, complete the coordination or restore the approved cadence and verify it. If restoration fails, report the scheduling failure and explicit manual continuation route; do not leave an active handoff described as waiting only for the user.
- Keep prompts compact, retaining essential authority boundaries and mandatory reads of verified authoritative checkpoints. Reuse existing state for decisions/history instead of repeatedly appending historical narrative or creating another controller.
- Use proportionate local verification. Observe the first actual pause, worker notification and resumption, or backoff and reset, during ordinary authorized runs; do not trigger implementation or create extra monitoring solely to test them. Until observed, distinguish policy simulation and saved configuration from scheduler/model behavior and actual wakeup/token savings.
